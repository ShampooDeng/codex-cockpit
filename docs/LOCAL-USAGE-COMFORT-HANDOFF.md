## 2. 已确认现象及证据边界

| 现象 | 已检查到的证据 | 结论 |
| --- | --- | --- |
| 使用一天后，用量页面仍显示 0 Token | 本机 Codex 会话中存在当天及前一天的正数用量事件；本机未配置云同步、旧同步或旧 `.tokei` 身份；成员没有关联设备 | 不能将界面的 0 理解为真实零用量；本机身份和汇总接入存在缺口 |

## 3. 根因与代码入口

### P0：纯本地统计依赖不存在的设备身份和既有快照

1. `src-tauri/src/codex_project_usage.rs` 的 `get_codex_project_usage_with_catalog` 按 `CODEX_HOME` 或默认目录扫描会话；采集器的设备标识来自旧 `.tokei/config.json`。
2. `src-tauri/src/usage_sync.rs` 的 `get_codex_project_usage` 仅在存在同步配置时通过 `identify` 补设备标识。纯本地新用户没有稳定身份来源。
3. `src-tauri/src/tokei_usage.rs` 的 `get_tokei_usage` 读取旧/托管聚合快照，不能独立把采集到的本机会话转成设备日账。
4. `src/lib/tokeiUsage.ts` 的 `withLiveLocalUsage` 在没有 `projects.deviceId` 或没有同 ID 的既有设备时直接返回原数据。它只能更新既有设备，不能让首个本机设备进入统计。

因此，仅生成一个设备 ID 或仅改 UI 的零值文案都不能修好整条流程。

### P0：体验记录与用量面板使用的数据不一致

`src/lib/useComfortUsage.ts` 的刷新只取得 `getTokeiUsage()`；调用 `getProjectUsage()` 仅提取设备 ID，不合并实时采集用量。用量面板在 `CodexUsagePanel.tsx` 有额外的本机合并逻辑，体验记录没有。只修用量面板可能使图表恢复而体验记录仍然为空。

`src/components/TeamMemberSettings.tsx` 的可分配设备来自已有用量设备和云端设备，也需让纯本地设备被发现。

### P1：单人身份初始化缺失

- `src/components/PersonComfortSection.tsx` 从分组列表选择体验所属人。
- `src/components/ComfortHistoryCalendar.tsx` 在无 personId 且无旧记录时禁用填写。
- `src/App.tsx` 的 `saveComfortFeedback` 有 `if (!personId && !existing) return`。

不能只删除禁用条件，让新记录以无归属旧记录的形式保存。必须先有稳定的本地个人身份，并正确关联本机设备。

### P1：曲线依赖额度百分比，旧不可用快照会持续保留

- 当前实际使用的是 `ComfortCurvePanel`，横轴为个人估算用量百分比；不是 `TokenComfortCurvePanel` 的 Token 横轴。
- `src/lib/personQuotaAllocation.ts` 的 `buildPersonQuotaAllocation` 需要有效的共享额度参考及可用成本日账，按个人成本占比分摊。当前记录的这两类数据均不可用。
- `src/lib/personComfort.ts` 的 `allocationForFeedback` 只要已有 `quotaAllocation` 就返回；`backfillPersonAllocations` 同样跳过已有对象，包含 coverage 为 unavailable 的对象。
- `src/lib/comfortFeedback.ts` 的 `usableFeedbackRecords` 排除缺少百分比或 coverage 不可用的记录；图表的 sampleCount 是可用于曲线的条数，不是全部已保存反馈条数。
- `src/App.tsx` 的“刷新快照”在额度分摊不可用时提前返回，连已经能够恢复的 Token 快照也不更新；错误统一称为金额不足，可能掩盖实际缺少历史额度参考的情况。

## 4. 建议实施方案

### A. 建立独立于同步的本机身份

在 Rust 应用配置域建立统一的身份解析与持久化入口，供采集、用量、组员和云同步设置使用。可新增 `local_identity.rs`，文件名可随现有风格调整。

- 优先沿用已绑定云同步/旧同步身份，再兼容有效旧身份；没有时生成并原子保存一个本机稳定 ID。不要用所有机器共享的常量 ID，不读取硬件序列号或账号凭据。
- 并发首次初始化与重启必须返回同一 ID；持久化失败需明确报错，不能每次生成临时新身份。
- 本机身份文件不能被解释为同步配置，不能触发上传或创建空间。
- 云同步设置页当前会自行生成 ID（`CloudSyncSettings.tsx`）；改为使用统一入口。未来首次加入同步沿用本机 ID，已有绑定不重写。
- 若已有互相冲突的身份，保留既有云端绑定，明确处理本地映射与重复统计，不静默重新登记设备。

### B. 统一本机与同步用量的读取结果

优先让原生 `get_tokei_usage` 返回包含本机采集日账的统一结果，使所有调用方得到同一份个人用量；不要只在某个 React 面板补数。

- 将采集结果投影为 `DeviceUsage` 的纯函数独立出来，便于合成数据测试。复用当前采集器缓存、并发限制、计数去重和定价逻辑，不新增第二套会话解析器。
- 无历史快照时也能插入本机设备。有同 ID 的已同步设备时合并或替换相应日期，不能相加导致重复统计。其他设备保留。
- 完整性按实际数据保留：缺价仍为 null；没有数据不能伪装成完整的零。实时采集、任务列表、模型汇总及设备日账必须一致。
- 部分扫描不得覆盖已有完整历史；首次只有部分数据可展示已知量并明确标记，但不能把扫描前缀当全天总量。不要为便捷丢掉原有 `scan_limit` 防护。
- 采集异常、忙碌或超时保留上次有效数据，呈现 stale/partial/unavailable；不要使远端设备数据一并消失。
- 调整 `CodexUsagePanel` 的额外合并以避免重复应用；同步更新 `useComfortUsage` 的状态、刷新返回值和保存时读取，防止状态已更新但保存拿到旧结果。
- 核查调用关系避免 `get_tokei_usage`、采集器和同步函数递归或锁等待。原生读取不调用上传流程。
- `TeamMemberSettings` 在尚无用量事件时也应能列出本机设备，区分“设备存在”与“设备已有日账”。

### C. 让单人用户无需手动添加组员即可记录体验

- 新的纯本地配置初始化一个持久化的个人身份，默认显示“我”，仅关联本机；可在设置中改名。选择状态、反馈 personId 和设备归属使用稳定 ID。
- 已有明确本机归属时复用，不能每次打开创建新组员。
- 已有自建组员或历史反馈时，不根据“只有一个组员”或名称相同推断这是本人。提供一次清楚的“将本机归属给该成员”操作，并通过现有保存接口维护 revision。
- 对当前这类“已有反馈、成员无设备”的配置，绑定原成员是保留历史连续性的优先恢复路径；若用户选了新本地身份，旧记录应仍可查看，不自动改归属。
- 多人、云空间已有归属不得被本地默认值覆盖；其他人的手调计划与反馈不得合并。无归属旧记录继续保留。
- 同步更新项目说明中“成员初始未配置”的描述，明确本地个人身份与加入共享空间的区别。

### D. 分开保存反馈、更新 Token、更新额度估算

- 有个人身份即可保存主观体验；即使用量未知，日历和记录详情也应明确显示“已保存体验；用量暂不可用”。
- 将刷新动作拆成独立结果：可重算 Token 时保存 Token 快照；额度参考和成本足够时再更新个人百分比。一个不可用不能阻止另一个更新。
- 对已有 unavailable 快照提供“更新用量”操作，允许可靠的新结果替换不可用部分；自动回填只用于所属人与日期都明确、数据完整且确实改善覆盖率的情形。
- 已有完整快照不随轮询自动重写；刷新失败保留原数据。保留原体验、personId、记录时间与日期，仅按现有约定更新更新时间及恢复字段，兼容同步合并规则。
- `backfillPersonAllocations` 需处理“已有对象但不可用”，同时避免重复持久化、无限刷新、把部分结果降级覆盖完整结果。
- 成本缺失、历史额度缺失、设备未关联、采集失败要区分提示。缺失的历史百分比不能从 Token、当前剩余额度或日后数据推算，更不能填零。
- 本次先保持既有百分比曲线语义，不自动切换成 Token 曲线，也不因仅有本机数据就认定共享账号全部消耗属于本人。

### E. 明确展示保存记录和可拟合记录的区别

- 曲线旁显示“已保存 N 条体验，其中 M 条可用于曲线”。无有效点时说明缺少什么数据。
- 无横坐标的反馈保留在日历/详情，不在百分比图上人为放到 x=0。
- 有真实百分比的反馈应立即显示点；没有历史额度参考的旧记录允许长期呈现“已保存、待补充用量”，而非承诺所有历史点都能恢复。
- 用量主面板区分加载中、无记录、读取失败、部分数据和真实零值，避免统一显示 0 Token。

## 5. 实施顺序与检查点

1. 用合成输入锁定四个复现：纯本地无身份、无既有设备、无成员、已有 unavailable 反馈。先添加能失败的关键回归测试。
2. 实施 A、B，先验证不开启同步也能看到非零本机用量，体验记录与主面板取数一致。
3. 实施 C，验证首次使用与已有成员升级路径，保留旧反馈归属。
4. 实施 D、E，验证 Token 可恢复而额度不可恢复时仍有清楚、真实的展示。
5. 运行目标测试及 SOP 快速交接检查，再做原生窗口验收。交付列出已完成和待验证项。

## 6. 回归测试与验收矩阵

所有 fixture 使用虚构成员/设备/模型/会话，例如 `local-test-device`、`person-a` 和固定日期 2026-09-09；禁止复制本机真实数据。用受控时钟避免与执行日期耦合。

| 场景 | 预期 |
| --- | --- |
| 无云配置、无 `.tokei`、无设备快照，但有正数会话用量 | 启动后可见本机用量；无需服务器；全程无同步请求 |

| 旧同步/云同步已有设备身份 | 沿用绑定，不重新生成，不重复累计 |

| 首次部分扫描/采集超时/记录被占用/未知模型价格 | 显示真实覆盖情况，保留已知量；缺价不是零；不误报完整 |

| 已有成员无设备且已有体验 | 可将本机关联原成员；不改 personId、不删反馈、不合并他人记录 |
| 主面板与体验保存 | 使用相同日期口径下的设备日账，Token 合计一致 |
| 有主观反馈但用量 unavailable | 保存成功、日历可见、已保存计数正确，曲线说明未参与原因 |
| 旧快照 unavailable，之后得到 Token、仍无历史额度 | Token 恢复；百分比仍未知；反馈保留；不出现虚构曲线点 |
| 旧快照 unavailable，之后取得可靠成本和历史额度 | 可更新个人估算，曲线出现该点；体验和归属不变 |
| 重复回填/失败/旧包回滚 | 无无限写入、无数据降级；原始记录和完整快照可保留 |
| 多人切换、共享设置 revision 冲突 | 不串人、不覆盖他人计划；冲突走既有协议 |
| 本地自然日、UTC+8 展示日与 04:00 额度使用日边界 | 沿用并明确原有口径，不在本任务批量迁移历史日期 |
