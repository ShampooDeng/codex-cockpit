# 独享账号额度与舒适曲线：补充修改计划

日期：2026-10-10（Asia/Singapore）。

## 1. 范围与交付状态

本次用户要求：针对“仪表盘已有额度百分比，体验仍无法用于曲线”制定修改计划并保存本地。仅交付方案，不实施代码、配置迁移、构建或安装。

本计划接续 [本机用量修复交接](LOCAL-USAGE-COMFORT-HANDOFF.md) 和 [实施记录](LOCAL-USAGE-COMFORT-IMPLEMENTATION.md)。前一轮已经修改了本机身份、日账接入和 Token 独立恢复；不要重复实施或覆盖已有更改。本计划补充“独享账号如何使用已有额度参考”，仍保留共享账号不凭本机成本推断全部归属的约束。

实施前重新检查工作区及运行版本，阅读 [AGENTS.md](../AGENTS.md)、[桌面开发 SOP](DESKTOP-DEVELOPMENT-SOP.md) 和 [测试矩阵](TEST-MATRIX.md)。当前源码与最初报告的 beta.5 已有差异，不应将本计划中的新限制全部归因于原始发布包。

## 2. 问题已明确

### 2.1 不是所有记录都缺额度

只读检查发现，两条反馈的情况不同：较早的记录没有历史额度参考；较新的记录已保存有效账号额度百分比，但个人百分比仍为 null。仪表盘截图也显示已用额度，因此不能把所有记录概括为“读不到额度”。

截图中的三个数值含义不同：

- 14%：当时记录的账号额度消耗参考。
- 11.2%：当天计划上限。
- 125%：14 ÷ 11.2 × 100，表示相对计划的使用比例，不能作为曲线的额度消耗横坐标。

测试应使用独立合成数据，例如已用 18%、计划 12%、计划使用比例 150%，不复制用户记录。

### 2.2 纯本地模式被统一排除

`src/lib/personQuotaAllocation.ts` 的 `buildPersonQuotaAllocation` 在 `data.localOnly` 为真时直接返回不可用分摊，即使已有真实额度参考。这样可以避免误把共享账号总量归给本人，但也阻止明确独享账号的本地用户使用曲线。

根本问题是把“采集范围只有本机”与“账号是否多人共用”当作同一条件。独享账号也可能有多台设备；开启同步也不意味着账号多人共用。不能简单删除 `localOnly` 判断并对所有人使用账号总量。

### 2.3 提示只解释第一条原始记录

`src/components/PersonComfortSection.tsx` 在样本数为 0 时，把 `records.find(...)` 找到的第一条原始记录交给 `missingComfortUsageReason`。它没有逐条解释，也没有使用用于曲线的派生结果。

后果：第一条的“缺历史额度”被当作所有记录的原因；即使部分记录已有效，其余被排除记录也没有汇总提示。调整记录顺序还可能改变提示。

## 3. 产品行为方案

### 3.1 明确账号使用方式

新增一个本地设置入口，可从舒适曲线的阻塞提示进入：

- 未确认：不默认将账号总量归给个人，提示选择使用方式。
- 仅我使用：用户明确指定一个稳定成员 ID 作为本人，在声明覆盖的日期内，允许使用真实账号额度参考作为该成员的曲线横坐标。
- 多人共用：保持现有成本分摊规则；本机数据不足时说明缺少全账号分摊依据。

界面可只展示两个可选选项，内部仍保留初始未确认状态。不要根据组员数量、是否联网、是否开启同步或成员名称自动认定独享。

此设置仅控制本地额度解释，不开启同步、不修改共享成员归属或他人的计划。“仅我使用”不是读取账号凭据进行身份核验。

### 3.2 独享账号的数据使用规则

优先使用该条反馈保存的有效额度参考；没有时才查找相同使用日期的既有官方历史/本地额度历史，复用 `buildComfortPrompt` 的来源与日期约束。

- 有有效参考且声明匹配所属人及日期：个人曲线横坐标等于账号参考，例如合成的 18%。
- 覆盖率为 partial 仍可成为有效点，沿用现有降低权重逻辑，并保留“不完整采集”提示。
- 不要求 Token 日账、模型价格或成本齐全；这些与直接采用独享账号额度参考是不同条件。
- 参考缺失、无效、未来日期或归属不匹配：继续保存体验但不生成曲线点。
- 不用今天额度填昨天记录，不用计划使用比例、剩余额度、Token 或预算推算历史参考。
- 合法的 0% 不能被当作缺失；仍遵守现有最大值与累计使用超过 100% 的处理。

仪表盘的“基准后已用”与历史额度可能存在观察时间和日界差异。必须复用可验证的历史参考，不能直接抓取界面当前数字，也不承诺任意时刻曲线与仪表盘数值完全相等。

### 3.3 历史范围与账号变化

采用本地持久化的声明记录，至少包含模式、personId、生效日期与声明时间。概念字段可为 `mode`、`personId`、`effectiveFrom`、`declaredAt`；实际存储沿用仓库可验证、原子保存的配置机制。

- 默认从用户选择的当天生效；对已有反馈提供明确的“也应用到所选历史日期”动作，不静默将过去的共享使用变成独享。
- 模式变化记录生效区间，过去已确认的解释不因切换而悄悄变化。重叠/冲突区间要有确定的更新规则。
- 声明限定到当前本地 Codex 配置及本人身份，不能作为全机器所有账号的全局开关。优先复用现有安全的账号/配置边界；若无法可靠识别账号切换，明确提示重新确认，不为此新增凭据读取或保存原始账号标识。
- 本人被删除或归属不明确时暂停直接归属，不选择列表中的下一人。
- 声明不进入共享设置和同步载荷。其他设备未确认时，不自动继承独享假设。

## 4. 技术方案与修改入口

### 4.1 保留成本分摊协议，新增显示用解释结果

建议新增纯函数 `resolveComfortUsage`（名称可调整），为每条记录返回统一结果：

- `usedPercent`、`coverage`、来源/采样时间。
- `basis`：如 `exclusive-account`、`cost-share`、`legacy`、`unavailable`。
- `reason`：结构化不可用原因；有效结果没有阻塞原因。

独享分支依据本地声明和真实参考生成显示结果；共享分支调用现有分摊逻辑。无归属旧记录维持既有兼容规则，不自动认领。日期、个人身份、模式的判定集中在该函数，避免 UI 与保存逻辑各写一套。

重要兼容约束：

- `ComfortQuotaAllocation.metricVersion` 当前仅为 `cost-share-v1`。
- TypeScript 的 `normalizeComfortQuotaAllocation` 会根据成本重算分摊；Rust 的 `comfort_sync.rs` 和 Worker 的 `snapshot-schema.js` 也校验这一格式。
- 因此不能为了独享分支填入虚构 `personCostUsd=1`、`totalCostUsd=1` 或把直接归属伪装成成本分摊；也不能仅扩展 TypeScript 类型而漏改存储/同步校验。
- 本次推荐不改变 `cost-share-v1`：原始反馈继续保存真实账号额度参考；独享声明单独本地保存，个人显示结果运行时派生，不回写成成本分摊，不发送给服务器。
- 原有有效成本分摊快照保留。若用户明确将某个历史区间改为独享，显示结果按该声明选择来源，原快照仍保留供审计/回滚；不得被旧分摊优先返回逻辑遮盖。

### 4.2 所有使用个人曲线的位置接入同一结果

重点检查并调整：

- `src/lib/personComfort.ts`：`personalFeedbackView`、`allocationForFeedback`、`missingComfortUsageReason` 及回填行为。
- `src/components/PersonComfortSection.tsx`：曲线、日历、可用计数及原因汇总。
- `src/components/ControlCenter.tsx`：这里也预先计算 personalFeedbackView/曲线，必须传入相同声明，避免覆盖子组件的新结果。
- `src/components/ComfortHistoryCalendar.tsx`：百分比当前依赖 `quotaAllocation`，需支持独享显示结果，否则曲线有点但日历仍空。
- `src/App.tsx`：反馈保存、刷新、提醒、声明读取及更新；更新用量仍保持 Token 与额度独立恢复。已有合法原始参考应能用于独享显示，不强制再采集 Token。
- 设置页、`src/types.ts` 及本地配置序列化：声明持久化、验证、错误提示、重启恢复。新存储不加入云载荷。

不要把派生视图当作原始反馈写入 `runtime-state`：`observedUsedPercent` 在原记录中仍表示保存的账号参考，个人视图可以使用解释后的数值。

## 5. 提示修复方案

用同一个解析结果决定是否参与曲线和显示原因，避免“实际已可用却仍提示缺失”。仅对当前选中成员统计。

原因建议分为：

| 原因 | 用户提示方向 |
| --- | --- |
| 未确认使用方式 | 选择“仅我使用”或“多人共用” |
| 历史额度参考缺失 | 对应日期未记录额度；Token 更新不会补出该百分比 |
| 多人分摊数据不足 | 已有账号额度，但缺少个人占比依据 |
| 声明不覆盖日期/本人不匹配 | 确认适用日期或所属人，不自动改归属 |
| 数据读取失败且无可用保存参考 | 保留体验，说明读取失败 |

局部 Token 采集失败不应遮挡独享模式中已有有效额度参考的使用，也不应被误报为额度缺失。

页面总计改为类似“已保存 2 条体验，1 条可用于曲线”；剩余记录按原因分组计数，日历详情逐日显示。即使已有部分有效点，也要能查看无效记录的原因。不要仅在 sampleCount 为 0 时显示解释。

统一表述“用于曲线”与现有日期、有效值、权重规则，避免提示计数与实际图中的点数不一致。不要承诺缺失历史额度以后必然恢复。

## 6. 合成回归测试与验收

固定时钟与日期，使用虚构个人和设备，覆盖：

| 场景 | 预期 |
| --- | --- |
| 本地模式，已确认独享，参考 18%、partial，成本为空 | 曲线有 18% 的点，保留 partial；不需要成本 |
| 同样数据，未确认使用方式 | 不自动认领，明确提示选择 |
| 同样数据，多人共用 | 维持分摊约束，不把账号总量给一个成员 |
| 计划 12%、参考 18%、仪表盘比例 150% | 曲线使用 18%，不使用 150% |
| 昨日无参考、今日有参考且独享声明覆盖 | 两条已保存、一条可用；逐日原因正确 |
| 颠倒上述记录顺序 | 计数与原因不变 |
| 参考为 0、partial 或合法累计值超过 100 | 按现有规则显示，不当缺失、不截断为 100 |
| 独享参考有效但 Token 采集失败 | 已有额度点保留，Token 单独报错 |
| 声明本人不匹配、成员删除、声明日期不覆盖 | 不给其他人/日期分配额度 |
| 修改声明范围、重启、重复刷新 | 范围可追溯，声明稳定，无重复记录或无限写入 |
| 原记录已有有效成本分摊，明确确认该历史范围独享 | 显示按选定模式解释，原分摊与原体验均保留 |
| 关闭独享或重新确认账号 | 不静默重写历史、不过度沿用其他账号假设 |
| 声明文件写入失败、损坏或旧版读取 | 明确失败、保留原始记录，安全回退到未确认 |
| 云同步往返/旧客户端 | 不上传独享声明或虚构成本；既有 cost-share 数据结构不变 |

优先扩展 `personComfort.test.ts`、`personQuotaAllocation.test.ts`、`PersonComfortSection.test.tsx`、`ComfortHistoryCalendar.test.tsx`、`App.comfort.test.tsx` 与 `ControlCenter.test.tsx`；为新声明存储/解析增加针对性测试。序列化和同步边界使用现有 `comfortSync`/Rust 校验测试证明没有泄漏或格式回归。

验证按桌面 SOP 和届时用户约束执行。此前实施记录注明有尚未完成的 Rust 编译及原生验收，不得把那些结果视作通过。本轮只写计划，不运行测试或构建。

原生验收至少确认：选择独享及适用日期后，有有效参考的反馈出现曲线点；日期详情与计数一致；原先缺失历史额度的记录仍诚实地显示不可用；重启后选择保留。记录源码版本、实际运行版本及未完成验证项。
